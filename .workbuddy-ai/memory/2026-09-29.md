## PRD + Skema DB ZKTeco iClock/ADMS Push Protocol

Dokumen yang dibuat: `docs/PRD-ADMS-PUSH.md`, `docs/PROTOCOL-SPEC.md`,
`docs/SCHEMA.md`, `migrations/001_init_adms_push.sql`.

### Temuan protokol yang WAJIB diingat (dari perangkat keras nyata)

Hasil riset dari `s0x90/zkteco-adms` (diverifikasi di firmware ZAM180-NF
v1.1.17) — datasheet resmi ZKTeco sudah **usang**:

1. **`USER ADD` / `USER DEL` DITOLAK device dengan `-1002`.** Datasheet
   mencantumkannya, tapi firmware nyata menolak. Yang benar:
   `DATA UPDATE USERINFO` dan `DATA DELETE USERINFO`.
2. **`DATA DEL` (singkatan) juga gagal** — harus `DELETE` penuh.
3. **`DATA QUERY` tidak mengembalikan data di balasan perintah.** Data dikirim
   terpisah lewat `POST /iclock/cdata?table=USERINFO`.
4. **Pemisah field perintah = TAB**, bukan spasi (nama bisa mengandung spasi).
5. **Newline/CR di nilai field = command injection** ke wire protocol
   (`C:<ID>:<CMD>\n`). Wajib ditolak saat validasi.
6. **Respons `/iclock/cdata` harus `text/plain`** — device tidak parse JSON.
7. **Handshake harus CRLF**, bukan LF.
8. **`TransFlag` salah set = device tidak pernah kirim ATTLOG.** Ini penyebab
   paling umum "device connect tapi tidak ada data".
9. **`TimeZone` jangan dikirim** — menggeser jam device & merusak timestamp.
10. `Return=-1004` = tabel/fitur tidak didukung model; harus menonaktifkan
    perintah sejenis untuk device itu.

### Empat endpoint wajib
`GET /iclock/cdata` (handshake) · `POST /iclock/cdata` (data) ·
`GET /iclock/getrequest` (poll perintah) · `POST /iclock/devicecmd` (konfirmasi).
Semua perintah ke device **hanya** lewat balasan `getrequest`.

### ATTLOG punya 3 varian format yang harus ditangani
A: 5 kolom tab (`PIN · DateTime · Status · Verify · WorkCode`)
B: 6–11 kolom tab (kolom 3+ reserved)
C: `key=value` (`PIN= · DateTime= · Verified= · Status=`)
Timestamp bisa `YYYY-MM-DD HH:MM:SS` **atau** Unix epoch.

### Keputusan skema yang penting
- **`attendance_log.record_hash` = SHA1(device|pin|punch_at|status|verify|work_code)
  dengan UNIQUE index.** Ini inti ketahanan: device memang kirim ulang saat
  jaringan putus. Hash **tidak memakai `Stamp` device** karena perilakunya
  berbeda antar firmware.
- `punch_at` = waktu **device**, bukan server (punch offline harus tetap benar).
- `attendance_log.device_id`/`employee_id` pakai **ON DELETE SET NULL**, bukan
  CASCADE — hapus karyawan **tidak boleh** menghapus riwayat absensi.
  (Sudah dibuktikan: delete employee → attlog tetap ada, employee_id jadi NULL.)
- `employee.pin` = VARCHAR bukan INT (PIN berawalan nol seperti `0012`).
- `command_queue.command_id` dipisah dari `id` tabel: ID wire protocol harus
  naik monoton & unik lintas device.
- `iclock_request` menyimpan body mentah semua request → bisa proses ulang
  setelah parser diperbaiki.
- `device.status='pending'` untuk device baru: tetap dilayani saat handshake
  (kalau tidak, device berhenti mencoba) tapi datanya belum dipercaya.

### Verifikasi yang sudah dilakukan (nyata, bukan klaim)
Skema dijalankan ke **MySQL 8.0.15 sungguhan** memakai instance sekali-pakai
di `%TEMP%\adms_schema_check` (Laragon, `--no-defaults`, port 3399 — instance
ini sudah dihapus setelah selesai):

- Migrasi sukses, exit code 0, 7 tabel dibuat.
- Idempotensi: insert pertama `ROW_COUNT()=1`, kirim ulang `=0`, total tetap 1 baris.
- `ON DELETE SET NULL`: hapus employee → baris attlog tetap ada, FK jadi NULL.
- `command_queue`: ACK → status `acked`; perintah `sent` >15 menit → `pending`
  dengan `attempt_count=1`; yang baru 1 menit tetap `sent` (tidak tersentuh).
- `UNIQUE uk_cmd_command_id` menolak duplikat ID (`ERROR 1062`) — korelasi aman.

### Catatan lingkungan (penting untuk sesi berikutnya)
- `mysqld --port=3399` **diabaikan** karena `my.ini` Laragon memaksa port 3306.
  Harus pakai **`--no-defaults`** + port eksplisit.
- `mysql -h localhost` resolve ke named pipe/socket dan bisa nyasar ke MySQL
  pengguna (PID 9880, port 3306). Selalu pakai `-h 127.0.0.1 -P <port>
  --protocol=TCP` untuk instance sementara.
- **MySQL pengguna di port 3306 JANGAN disentuh.** Password root-nya tidak
  diketahui dan instance itu milik pengguna.
- Proses background (`mysqld ... &`) **dimatikan di antara panggilan tool**.
  Jalankan server + migrasi + verifikasi + shutdown dalam **satu perintah**.
- User-defined variable (`SET @x`) **hilang antar pemanggilan `mysql`**;
  pakai `INSERT ... SELECT id FROM device` agar mandiri.
- Path gaya Git Bash (`/c/...`) tidak diterima PHP/native; pakai `C:/...`.
